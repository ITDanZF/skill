# 编码工作流

这个工作流适用于代码编写、修改、调试、重构、测试和代码审查任务。它采用分级策略：简单任务走轻量对话确认，复杂或高风险任务才走完整中文 Markdown 分析文档。

## 工作流分级

### 轻量流程

适用于：

- 单文件或少量局部修改。
- 行为边界清晰。
- 不涉及公共 API、数据契约、权限、安全、迁移或复杂兜底。
- 不需要架构拆分或多方案决策。
- 风险低，可以用快速检查验证。

轻量流程直接在对话中给出：

- 简要分析。
- 修改建议。
- 涉及文件。
- 风险与验证方式。
- 一个明确确认问题和 2-4 个可选项。
- 等待用户确认后修改。

### 完整流程

适用于：

- 多模块、多文件或跨层变更。
- 新功能开发、架构调整、公共 API 或数据契约变化。
- 需求、验收标准、影响范围或风险不清楚。
- 涉及兜底、重试、默认值、静默忽略、降级策略。
- 可能影响安全、隐私、权限、计费、数据正确性或生产稳定性。
- 用户要求正式分析文档。

完整流程需要生成中文 Markdown 分析文档，并在用户批准前不修改源代码。

## 对话确认规则

任何需要用户确认的问题，都必须在对话框中直接给出。Markdown 文档只能作为记录，不能替代对话确认。

确认问题使用类似 Cursor 的格式：一个问题，提供 2-4 个选项，每个选项说明影响或取舍。选项要互斥、具体、可执行。

推荐格式：

```markdown
需要你确认一个点：<一个明确问题>

1. <选项 A>：<选择后的影响或取舍>
2. <选项 B>：<选择后的影响或取舍>
3. <选项 C>：<可选，选择后的影响或取舍>
```

如果有推荐选项，把推荐理由写清楚：

```markdown
我推荐选项 1，因为它改动最小，风险最低。
```

一次尽量只问一个阻塞问题。多个问题都阻塞时，最多一次问 3 个，并分别给选项。

需要对话确认的典型场景：

- 是否采用完整 Markdown 分析流程。
- 是否接受某个修改方案。
- 多方案选择。
- 是否添加兜底、重试、默认值、兼容 shim 或静默忽略。
- 是否偏离当前模块已有写法。
- 是否运行耗时检查，例如完整构建或全量测试。
- 是否扩大修改范围或顺手重构。

## 用户跳过完整流程

如果用户明确说跳过繁重流程、直接改、不要文档、快速处理等：

- 可以跳过完整 Markdown 分析文档。
- 仍然需要在对话中给出最小必要分析、修改点和风险。
- 仍然不能无脑兜底。
- 如果存在破坏性操作、安全/隐私风险、数据丢失风险、生产迁移风险或验收标准不清，必须先问清楚，不能直接跳过。

## 分析维度

根据任务复杂度选择必要维度。轻量流程只覆盖关键维度；完整流程覆盖更多维度。

- 需求与验收标准：用户目标、期望行为、非目标、成功信号。
- 工程上下文：技术栈、包管理器、框架、运行时、构建和测试命令、本地说明。
- 架构边界：模块职责、公共 API、集成点、依赖方向、分层关系。
- 当前行为：相关调用链、数据流、状态变化、副作用、错误处理。
- 根因分析：当前行为为什么错误、不完整、有风险或缺失。
- 现有规范：命名、结构、错误处理、校验、日志、测试、代码风格、抽象方式。
- 涉及文件：可能修改的文件、已阅读的上下文文件、可能需要补测试或文档的文件。
- 影响范围：用户、API 调用方、数据兼容、迁移、性能、安全、可观测性、部署。
- 风险评估：回归面、边界情况、并发、幂等、部分失败、回滚复杂度。
- 验证方案：优先快速、针对性验证，必要时才跑完整构建。

## 模糊边界门禁

在生成最终建议前，如果下面任何内容不清楚，必须先问用户：

- 期望行为、验收标准或优先级。
- 某个行为到底是缺陷、兼容要求，还是有意的产品策略。
- 数据契约、外部服务行为或 API 兼容要求。
- 安全、隐私、权限、计费、破坏性操作或合规影响。
- 兜底、重试、默认值、静默忽略或降级策略。
- 是否保留一个存在问题但已经形成惯例的模块写法。
- 多个方案取舍明显不同，需要用户选择。

问题要简洁、集中。不要靠猜测推进关键边界。

## 兜底策略

禁止无脑兜底。兜底包括任何隐藏或补偿失败、缺失数据、不兼容输入、外部服务错误、超时、非法状态或意外空值的代码路径。

添加兜底前，必须让用户确认：

- 兜底处理的失败模式。
- 兜底对用户是否可见，是否允许静默。
- 对数据正确性的影响。
- 日志、指标、告警或排障可见性。
- 如相关，确认重试次数、超时策略和回滚行为。

优先显式失败，避免静默制造数据错误或增加排障难度。

## 现有代码规范评估

修改前必须评估局部代码规范。

- 如果现有规范一致、合理，并且能完成任务，优先遵循。
- 如果现有规范不一致、有风险或阻碍任务，说明问题，并询问用户是继续沿用、最小偏离，还是重构该区域。
- 不要引入没有必要的新抽象；只有当它能降低真实复杂度，或明显匹配现有模式时才使用。

## 多方案输出

存在多个可行方案时，每个方案需要包含：

- 方案概述。
- 涉及文件。
- 优点。
- 风险与取舍。
- 验证成本。
- 适用场景。

随后给出推荐方案，但必须等待用户选择或批准。

## 快速验证策略

不要每次修改后默认运行 `npm run build`、完整编译或全量测试。优先选择更快的确认方式：

- 只运行受影响模块的单元测试。
- 使用测试过滤器，例如按文件名、用例名、package、workspace 或路径筛选。
- 运行类型检查、lint 或格式检查的局部命令，如果项目支持。
- 使用 `tsc --noEmit`、eslint 指定文件、vitest/jest 指定文件等项目已有快速方式。
- 对小改动进行 diff 自检和关键调用点检查。
- 对 UI 小改动做局部页面 smoke test 或截图检查。

只有在下面情况才优先考虑完整构建或全量检查：

- 修改构建配置、依赖版本、打包入口、路由入口、全局类型、公共组件库或共享基础设施。
- 修改影响范围无法用局部检查覆盖。
- 发布前或用户明确要求完整验证。
- 快速检查失败，且需要完整构建定位问题。

如果跳过完整构建，需要在结果里说明采用了哪些快速验证，以及剩余风险。

## 稳定预览策略

生成 Markdown 分析文档后，必须把文件路径发在对话框中。这个路径是最稳定的预览方式。

VS Code 自动打开只作为尽力尝试：

- 如果打开成功，仍然要在对话框中给出文件路径。
- 如果打开失败，不要把流程判定为失败；说明失败原因或状态，并给出文件路径。
- 如果用户需要，可以再请求权限或让用户手动打开该路径。
- 不要依赖 VS Code 自动打开作为唯一交付方式，因为桌面端、沙箱、PATH、已有窗口焦点和系统 GUI 限制都可能影响它。

脚本输出中的 `REPORT_PATH=` 是需要展示给用户的路径，`OPEN_STATUS=` 是自动打开尝试的结果。

## 临时文档策略

- 只有完整流程才生成临时分析 Markdown 文件。
- 过期时间设置为生成后约 3 天。
- 使用 `scripts/create_analysis_doc.py` 生成文件并清理旧分析文档。
- 默认放在仓库外的系统临时目录，避免污染源码仓库。
- 如果用户要求永久保留，需要移动到用户确认的文档目录。

## VS Code 打开方式

使用当前工作区路径运行：

```bash
python <skill-dir>/scripts/create_analysis_doc.py --workspace <workspace> --title <short-task-title>
```

脚本会打印 `REPORT_PATH=<路径>` 和 `OPEN_STATUS=<状态>`，并尽力调用 `code` 打开 VS Code。如果 VS Code 不可用或 GUI 打开失败，应继续汇报文件路径，并询问是否手动打开或授权重试。

## Large project verification budget

Do not use 
pm run build as the automatic final validation for large frontend projects. A full build may consume substantial time for a small AI change, so select the cheapest check that still covers the risk: touched-file lint/typecheck, focused unit tests, workspace/package-level tests, local smoke render, or screenshot comparison. Run a full build only when the change affects build configuration, shared type surfaces, routing/bundling/dependency behavior, release-critical paths, or when narrower checks fail or cannot provide enough confidence. If skipping full build, state the targeted checks used and the residual risk in the final response.
