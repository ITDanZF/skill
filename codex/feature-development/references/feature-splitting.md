# 新功能开发与模块拆分规范

这个规范用于新功能开发的上游判断。它不直接替代 `coding` skill；确认属于新功能开发后，仍然必须进入 `coding` 的中文分析、确认和审批流程。

## 任务分类

先判断用户请求属于哪一类：

- 新功能开发：新增用户可感知能力、业务流程、页面能力、接口能力、数据处理能力或系统集成能力。
- 现有功能增强：在已有能力上扩展行为、配置、入口、状态或兼容范围。
- Bug 修复：目标是纠正已有行为与预期不一致的问题。
- 重构：目标是改善结构，不改变外部行为。
- 测试、文档或配置：不直接改变产品功能。

如果判断为“新功能开发”或“现有功能增强”，先问用户确认是否按新功能开发流程处理。

## 拆分原则

不要把不断增长的功能全部揉在一个页面、一个组件、一个函数或一个文件里。也不要为了显得工程化而过度拆分简单功能。

合理拆分的目标是：

- 降低单个文件的理解成本。
- 隔离 UI、状态、业务规则、数据访问、校验、副作用和展示组件。
- 让核心逻辑更容易测试。
- 贴合项目已有目录结构和模块边界。
- 降低未来扩展、回滚和定位问题的成本。

## 需要考虑拆分的信号

出现多个信号时，应优先考虑拆分：

- 单个页面或组件同时承担展示、状态管理、接口请求、表单校验、业务规则和错误处理。
- 文件已经明显变长，阅读需要频繁上下滚动才能理解主流程。
- 新功能包含多个独立子区域、步骤、弹窗、表单、列表、详情或状态面板。
- 逻辑需要复用，或者未来很可能被其他入口复用。
- 业务规则可独立测试，但目前会被 UI 代码绑定。
- 异步副作用、缓存、权限、埋点、日志或错误处理让页面主流程变得混乱。
- 修改一个区域容易影响另一个无关区域。

## 不建议拆分的情况

出现下面情况时，保持简单通常更合适：

- 功能非常小，代码量低，职责单一。
- 拆分后文件数量增加，但每个文件只有极少逻辑，理解成本反而升高。
- 该功能是一次性或实验性能力，尚无明确扩展方向。
- 项目现有模式就是局部内聚的小页面实现，并且当前任务没有超出这种模式。
- 抽象名称无法稳定表达职责，只是为了拆分而拆分。

## 推荐边界

根据项目技术栈和现有模式选择，不要机械套用全部边界。

前端常见边界：

- Page/Route：路由入口、页面级布局、组合子模块。
- Feature container：功能编排、数据装配、权限或状态入口。
- Presentational component：纯展示或交互组件。
- Hooks/Composables：状态、数据请求、副作用、表单逻辑。
- Services/API：接口请求、数据转换、外部依赖。
- Domain helpers：业务规则、校验、计算逻辑。
- Types/Schema：类型、DTO、表单 schema、校验 schema。
- Tests：核心业务规则和关键交互测试。

后端常见边界：

- Route/Controller：协议入口和请求响应映射。
- Service/Application：业务用例编排。
- Domain：核心规则、状态转换、实体或策略。
- Repository/Gateway：数据访问或外部系统访问。
- DTO/Schema：输入输出结构、校验和转换。
- Tests：业务规则、接口契约、集成路径。

## 输出到分析文档的内容

在 `coding` 的中文分析报告中增加“新功能开发评估”部分，包含：

- 任务分类：是否新功能开发或现有功能增强。
- 用户确认：是否已确认按新功能开发流程处理。
- 功能范围：用户可感知的新增能力是什么。
- 拆分判断：需要拆分、暂不拆分，或需要用户选择。
- 判断依据：为什么这样拆或不拆。
- 推荐结构：建议新增或调整的模块边界。
- 备选方案：至少在边界不明显时给出多个方案。
- 风险：过度集中和过度拆分分别有什么风险。
- 下游动作：进入 `coding` 的审批流程后，哪些文件可能被修改。

可以使用下面的简短确认：

```text

```
