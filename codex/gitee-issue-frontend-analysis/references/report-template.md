# 问题分析报告结构

报告应让未参与排查的人也能区分事实、推断和待确认项。没有证据的章节保持简短，不补写虚构内容。

## 1. 结论摘要

- 一句话描述现象和最可能根因。
- 主责边界、协同责任、判定置信度。
- 推荐处理优先级及是否阻塞发布。

## 2. 问题单信息

列出 Gitee 链接、编号、标题、状态、优先级、环境、复现步骤、预期结果和实际结果。注明信息更新时间；来自附件或评论的重要补充单独标明来源。

## 3. 代码与运行证据

优先用表格表达：

| 证据 | 观察结果 | 支持的结论 |
| --- | --- | --- |
| Gitee 描述/附件/评论 | 事实 | 说明它支持或排除了什么 |
| 前端文件与行号 | 实际逻辑 | 与预期或接口契约的差异 |
| 接口、配置或运行结果 | 实际数据 | 根因或触发条件 |

本地文件使用绝对路径可点击链接。明确标注无法复现、无权限查看或没有日志支持的部分。

## 4. 原因分析

分别说明：

- 直接原因：导致现象的具体逻辑或数据差异。
- 根因：为什么该差异会进入当前实现。
- 触发条件：哪些状态、数据、权限或环境下出现。
- 排除项：检查过但不构成原因的关键路径。

## 5. 责任判定

| 项目 | 结论 |
| --- | --- |
| 主责边界 | 前端/后端/API/数据配置/产品需求/设计交互/部署环境/第三方/共同责任/暂无法判定 |
| 协同责任 | 没有则写“无明确协同责任” |
| 置信度 | 高/中/低 |
| 判定依据 | 引用第 3、4 节的关键证据 |
| 待确认事项 | 哪些证据会改变当前判定 |

使用中性措辞判定交付边界，不评价个人。

## 6. 修改意见

按优先级列出：

- 必须修改：形成最小闭环的改动。
- 建议优化：降低复发概率但不阻塞修复。
- 无需修改：被排除的端或模块，说明理由。

每项包含所属端、建议动作、预期行为和验证方法。存在多个方案时说明推荐方案及取舍。

## 7. 修改范围

列出直接修改文件或候选文件、调用链、接口字段、状态/权限/配置、测试用例和文档。区分“已确认影响”和“潜在影响”。

## 8. 风险与验证建议

用“风险等级（高/中/低）—风险—缓解或验证方式”描述。覆盖实际相关的回归、兼容、数据、接口时序、权限安全、性能和发布回滚风险，并给出最小测试矩阵。

## 9. 待补充信息

只列会影响责任判定、修改方案或风险级别的信息；若没有则写“无”。
